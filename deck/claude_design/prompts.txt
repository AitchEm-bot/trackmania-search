04 WHY IT IS A SEARCH PROBLEM
Headline: Find the fastest sequence of key presses through one track
Three stats: PHYSICS TICK 10 ms · CONTROLS 4 keys · POSSIBLE RUNS ≈10⁵⁰² (mint)
Definition row (mono labels): STATE the full car state at one tick · ACTION a key combination held for 50 ms · COST race time
Caption: 8 key combinations every 50 ms for 27.8 s: far too many to try, so the search needs a heuristic and pruning. The game is deterministic: the same state and inputs always give the same run, so a state can be saved, branched and replayed exactly.
NOTES: Frame it as a search problem. A state is the full car state at one physics tick. An action is a combination of the four keys held for 50 milliseconds, and the cost is race time. With 8 useful combinations every 50 ms over about 556 steps there are roughly 10 to the 502 possible runs, so exhaustive search is impossible. Determinism is what makes search possible at all: the same inputs from the same state always produce exactly the same result, so we can save a state, branch from it and replay it.

05 THE SYSTEM
Headline: The real game is the simulator
Three numbered columns on a thin mint line (big italic 01 02 03 in mint):
01 GAME: TrackMania Nations Forever + TMInterface 2.2.1 via ModLoader. Physics in 10 ms ticks.
02 OUR PLUGIN: SearchBridge (AngelScript). Save and restore the car state, step the physics, stream frames, over TCP.
03 SEARCH: tmsearch (Python). Beam search and local search drive the plugin.
Footer (mono, muted): deterministic · bit-identical repeats · finish blocked, so no run ever counts as a record
NOTES: The key design decision: we do not model the car. The game itself is the simulator. TMInterface 2.2.1, loaded through ModLoader, is a tool-assisted-speedrun mod that lets a plugin save and restore the full game state. We wrote our own AngelScript plugin, SearchBridge, with a small TCP protocol: save and restore a car state, step the physics with a set of keys held for N ticks, and stream frames back. Our Python package, tmsearch, runs the searches against it. The game advances in 10 ms physics ticks and is deterministic, so a state can be saved, branched and replayed exactly. The plugin blocks the finish so no search run is ever saved as a real record.

07 BEAM SEARCH
Headline: Beam search through time
Left, a two-column table (PART / DESIGN):
Step | 8 key combinations, each held 5 ticks (50 ms)
Beam | keep the best 40 states in each time layer
Score | progress along the reference line: ms ahead of my PB ghost, 0.3 s lookahead
Prune | off the line, 0.6 s behind, missed checkpoint, duplicates
Safety net | my own run rides along in every layer
Right, hero: label "RESULT AFTER 20 MIN", number 27.66 (mint), "▼ −0.16 s vs PB · beats gold", "177,163 expansions"
NOTES: Our first algorithm is a beam search layered by race time, with beam width 40. Every step holds one of 8 key combinations for 5 physics ticks, 50 ms, so all states in a layer share the same race time and can be compared fairly. The heuristic is progress along the reference line: how far ahead of my PB ghost a state is, projected 0.3 s forward using its speed. Pruning drops states that leave a corridor around my line, fall more than 0.6 s behind, or miss a checkpoint, and merges near-identical states. My own run is replayed alongside, so the result can never be worse than my PB. In 20 minutes it made 177,163 expansions and found 27.66: 0.16 s faster than my PB, already beating gold.

08 WHY IT STALLED

10 LOCAL SEARCH
Headline: Hill climbing on the key presses
Left, table (MOVE / WHAT IT DOES):
Shift | move a key press or release by a few ticks
Tap | add a short tap
Lift | come off the throttle briefly
Brake → lift | coast instead of braking
Steer nudge / shift | adjust or move the analog steering
Rule (muted): Kept only if the whole run finishes earlier. Rejected early once 150 ms behind.
Right, hero: label "FROM 27.66, 30 MIN", number 27.42 (mint), "▼ −0.24 s", "4,723 evaluations · 125 accepted"
NOTES: The second algorithm is local search: hill climbing over the input sequence. A move shifts a key press or release by a few ticks, adds a short tap, lifts off the throttle, replaces braking with lifting, or nudges or shifts the analog steering. Each candidate is re-simulated in the game from a cached state just before the change, all the way to the finish, and kept only if it finishes earlier. Candidates that fall 150 ms behind are rejected early. Unlike the beam, it judges every change by the full run, so it cannot be fooled by a short-term gain. In 30 minutes it evaluated 4,723 candidates, accepted 125, and brought the time from 27.66 to 27.42.

Caption: Any faster run is written to a shared best file and adopted by the others. Time warp re-aligns the rest of the run after an early change.
NOTES: To use more CPU we ran four copies of the game, each with its own plugin port and its own search worker, sharing one best-run file. Each worker tweaked a different section of the run; whenever one found a faster run it wrote it to the shared file and the others adopted it, a simple parallel hill climb. For early changes we added time warp: after a change, the rest of the run's inputs are shifted by the number of ticks the car gained, so they line up with the track again. The results were lopsided: in the first 20 seconds no tweak was faster, while the final section produced 111 kept tweaks. Together they brought 27.42 down to 27.28, 0.54 s under my PB.
